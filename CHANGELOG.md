## [1.0.0-beta.1] - 2026-10-15

### Added

- `money.CentAmount`, an `int64` money type counting whole cents, as the exact
  integer counterpart of the `float64` `money.Amount` for the common two
  decimal places case. It has no NaN or infinite states, so the valid range is
  `MinCentAmount` to `MaxCentAmount`, where `MinCentAmount` is one above
  `math.MinInt64` to keep negation total.
  Comes with `NullableCentAmount`, `ParseCentAmount(str, mode, decimals...)`,
  and conversions in both directions: `CentAmount.Amount`,
  `Amount.CentAmount(mode)`, `CentAmount.DecimalAmount` and
  `DecimalAmount.CentAmount(mode)`.
  `CentAmount.SplitEqually` and `CentAmount.SplitProportionally` apportion
  exactly: the parts sum to the initial amount, and no part is more than one
  cent from its fair share or carries the opposite sign. The `Amount` splits
  now apportion the same way, see Changed.
- `Enums()` and `EnumStrings()` on `country.Code`, `language.Code` and
  `money.Currency`, listing every valid code. They are generated by go-enum,
  pinned in `tools/go.mod`: run `./run-go-enum.sh` after adding a code, and
  CI fails if the generated methods are stale.
- `MarshalText` on `money.Currency`, `NullableCurrency`, `language.Code`,
  `country.Code`, `NullableCode`, `bank.IBAN`, `NullableIBAN`, `bank.BIC`,
  `NullableBIC`, `vat.ID`, `NullableID`, `date.Date`, `NullableDate`,
  `email.Address` and `NullableAddress`, writing the normalized value, or an
  invalid value unchanged, so `strfmt` and `encoding/xml` write them in the
  same canonical form as `Value` and JSON. `email.AddressList` and
  `NullableAddressList` write the list as stored. `encoding/json` writes map
  keys of string types as they are, without `MarshalText`.
- `UnmarshalJSON`, `UnmarshalXML` and `UnmarshalXMLAttr` on the same
  normalizing types, and `Scan` on `email.Address`, which read a value like
  `Scan`: normalized if it is valid, unchanged and without an error if not,
  see Changed. There is deliberately no `UnmarshalText` on them, so
  `encoding/json` reads the keys of a `map[money.Currency]V` as given, and
  two spellings of a currency stay two keys.
- `email.SplitAddressList` and `AddressList.SplitRaw` and
  `NullableAddressList.SplitRaw`, which split an address list at the commas
  between its entries, outside quotes, angle brackets and comments, and
  return the entries unchanged, without parsing or normalizing them.
  Like `ParseAddressList`, they keep the unquoted display name of
  `Doe, John <john@example.com>` in one entry.
- `email.AddressSet.NormalizedAddressList`, which returns the normalized
  addresses of a set, merged and sorted, as `AddressList`, and
  `AddressSet.MarshalText`, `UnmarshalText` and `UnmarshalJSON`, so an
  `AddressSet` works with `encoding/xml` as an address list.
- `email.NullableAddress.Valid`, so `NullableAddress` implements
  `types.NormalizableValidator`.
- `ScanString` on `language.Code`, `email.Address` and
  `email.NullableAddress`, so `strfmt.Scan` and CSV scanning store them
  normalized like the other normalizing types instead of as given.
  `NullableAddress` reads `NULL`, `null` and `nil` as null.
- `language.Code.Validate()`, which normalizes first like `country.Code` and
  `money.Currency` and returns the error of `Normalized()`, naming the input.
  So `types.Validate`, `types.DeepValidate` and `strfmt` scanning accept
  `"EN"`, `"eng"` and `"en-US"`, which `Value` and `MarshalJSON` write as
  `"en"`. `Valid()` accepts them too, see Changed.
- `ASCII()` on `email.Address`, `NullableAddress`, `AddressList` and
  `NullableAddressList`, returning the normalized form with non-ASCII names
  RFC 2047 encoded for message headers.
- `charset.GetEncoding` resolves IANA and MIME charset labels as they appear
  in HTTP and MIME headers, like `windows-1252`, `ISO-8859-1`, `latin1`,
  `US-ASCII` and `UTF-16`, through `golang.org/x/text/encoding/ianaindex`.
  A label of an encoding the package already lists returns that encoding, so
  `latin1` returns the `ISO 8859-1` encoding. Other supported charsets,
  including multi-byte ones, are wrapped in the generic `Encoding` and named
  by their MIME name. `htmlindex` is deliberately not used: it follows the
  WHATWG encoding standard, which maps `iso-8859-1` and `us-ascii` to
  `windows-1252`, and that is wrong for MIME.
- The current ISO 4217 currencies `MRU`, `SLE`, `SSP`, `STN`, `VED`, `VES`,
  `XCG` and `ZWG` as `money.Currency` constants, and the withdrawn `ZWL`
  (Zimbabwe Dollar 2009 to 2024) next to the other withdrawn codes kept for
  old data. `ANG`, `BGN` and `CUC` have been withdrawn by ISO in the meantime
  and stay as well. Fund codes, precious metals, bond units and test codes are
  deliberately not included.
- `money.Currency.MinorUnits()` returns the ISO 4217 minor units of a
  currency: 0 for currencies like `JPY` and `KRW`, 3 for `BHD`, `IQD`, `JOD`,
  `KWD`, `LYD`, `OMR` and `TND`, and 2 for all others, including invalid
  codes.
- `strfmt.MoneyFormat.FormatCentAmount`, `FormatDecimalAmount` and
  `FormatCurrencyDecimalAmount`. `strfmt.NewFormatConfig` and the English and
  German presets register formatters for `money.CentAmount`,
  `money.DecimalAmount` and `money.CurrencyDecimalAmount`, so they format
  like `money.Amount`: `CentAmount(123450)` formats as `1.234,50` with the
  German preset instead of `123450`, and a zero amount as `0,00` instead of
  the `Nil` placeholder. `money.NullableAmount`, `NullableCentAmount` and
  `NullableDecimalAmount` format like their amount type, and null as the
  `Nil` placeholder.
- `types.ValidOr(val, def)` and `types.ValidatedOr(val, def)` return `val`
  if it is valid by its `Valid` or `Validate` method, else `def`, like
  `types.ValidOr(status, StatusDraft)`. Unlike `types.Validate`, they call
  the method directly, so a nil func, interface or value receiver pointer
  panics.

### Changed

- **Breaking:** `date.Date.Normalized` and `NullableDate.Normalized` take no
  language hint, so that both implement `types.Normalizable` and
  `types.NormalizableValidator`. Pass the hint to the new
  `NormalizedLang(lang language.Code)`: `d.Normalized(language.EN)` becomes
  `d.NormalizedLang(language.EN)`. `Normalize`, `NormalizeNullable`,
  `NormalizedOrNull` and `NormalizedOrUnchanged` keep their optional hints.
- **Breaking:** the types with a `Normalized` method share one contract for
  reading and writing, see "Reading and writing values" in the README:
  `country.Code`, `money.Currency`, `language.Code`, `vat.ID`, `bank.IBAN`,
  `bank.BIC`, `date.Date`, `email.Address` and their `Nullable` variants.
  - `Scan`, `UnmarshalJSON`, `UnmarshalXML`, `UnmarshalXMLAttr` and
    `ScanString` without `validate` store a valid value normalized, a blank
    value as the empty value and an invalid value unchanged, without an
    error, so one invalid value doesn't fail a whole query or document and
    `Validate` reports it. They stored the text as given, and
    `date.Date.Scan` and `NullableDate.Scan` returned an error for an
    invalid date. A value read from SQL, JSON or XML is canonical if it is
    valid, so `==` and map lookups work on it. For some inputs the canonical
    form loses information, and a load-modify-save of the row writes it
    back that way: `language.Code` drops region and script subtags, so
    `"pt-BR"` is read as `"pt"` and `"zh-Hant"` as `"zh"`, and
    `money.Currency` reads the ambiguous symbols `"$"` as `"USD"` and `"¥"`
    as `"JPY"`, although `"¥"` is also the symbol of the Chinese yuan.
  - `Value` writes the normalized value and SQL NULL for a blank value, and
    returns the error of `Normalized` for an invalid value, because the
    database is where it would stay. It wrote an invalid value unchanged,
    and `money.Currency`, `language.Code`, `bank.IBAN` and `bank.BIC` wrote
    every value unchanged. Only the `date` types already returned an error.
    `vat.ID("")`, `bank.IBAN("")`, `bank.BIC("")`, `email.Address("")` and
    `email.AddressList("")` are written as SQL NULL instead of `''`, and
    `vat.ID.Scan(nil)` and `email.AddressList.Scan(nil)` read the empty
    value instead of returning an error, and the error of `vat.ID.Scan` for
    a wrong SQL type no longer wraps `vat.ErrInvalidID`. Because `Value` also encodes query
    parameters, `WHERE bic = $1` with `BIC("DEUTDEFF")` now sends
    `DEUTDEFFXXX`: normalize existing columns before comparing them with
    values written by this version, and check them for invalid values,
    which a load-modify-save of the row now refuses to write.
  - `MarshalJSON` and `MarshalText` write the normalized value, or an
    invalid value unchanged. `MarshalJSON` is new on `money.Currency`,
    `language.Code`, `bank.IBAN`, `bank.BIC`, `vat.ID`, `date.Date` and
    `email.Address`, `Value` on `email.Address`, and `MarshalJSON` now
    normalizes for `money.NullableCurrency`,
    `bank.NullableIBAN`, `bank.NullableBIC`, `vat.NullableID`,
    `date.NullableDate` and `email.NullableAddress`. A BIC is written with
    11 characters, `"BKAUATWW"` as `"BKAUATWWXXX"`.
  - `money.CurrencyAmount` and `CurrencyDecimalAmount` write the normalized
    currency in `Value`, JSON, `FormatSep` and the `strfmt` money
    formatters, `"jpy 1235.00"` as `"JPY 1235.00"`, and `Value` returns an
    error for an invalid currency.
  - The new value receiver `MarshalJSON` and `MarshalText` methods and the
    pointer receiver `UnmarshalJSON` and `UnmarshalXML` methods are promoted
    into structs that embed these types, which changes the JSON, XML and
    text form of such a struct to the embedded value; embed them as a named
    field instead. A pointer receiver `MarshalXMLAttr` writes the text of
    `MarshalText` and leaves out a nil pointer attribute field, like
    `Currency *money.Currency` with the tag `xml:"currency,attr"`, with or
    without `omitempty`. Without it `encoding/xml` would call `MarshalText`
    through the nil pointer and panic, as it does for a `*time.Time`
    attribute. A nil pointer `,chardata` field still panics, because
    `encoding/xml` has no such hook for it; use a non-pointer `,chardata`
    field.
- **Breaking:** the `String` method of the normalizing types is removed, so
  `fmt`, templates and logs show a value as stored instead of a normalized
  form that hid a non-canonical or invalid value. `country.Code`,
  `money.Currency` and `language.Code` keep the `String` that go-enum
  generates, which returns the stored code. Replace `x.String()` with
  `string(x)` for a value read from SQL, JSON or XML, which is canonical if
  valid, and with `x.Normalized()` for a value built with a conversion like
  `money.Currency(s)`. `money.CurrencyAmount.String`,
  `CurrencyDecimalAmount.String`, `bank.Account.String` and
  `email.Message.String` show the currency, IBAN, BIC and addresses as
  stored too. `date.NullableDate.StringOr` returns the date as stored and the
  alternative only for null, like the `StringOr` of the other nullable
  types. `date.Date.Format(date.Layout)` keeps writing the normalized date.
- **Breaking:** `language.Code.Valid` accepts every spelling that
  `Normalized` accepts, like `Validate` and the `Valid` of the other
  normalizing types, so `Code("EN").Valid()` is true. Use
  `ValidAndNormalized` to require the canonical code.
- `email.ParseMIMEMessage` returns an error for a message with more than
  10,000 MIME parts, the default limit of `github.com/jhillyerd/enmime/v2`
  v2.5.0, which protects against messages that would take very long to
  parse. Such messages were parsed before.
- **Breaking:** without a language hint, an ambiguous numeric date with
  slashes and the year last is read month first like in the US:
  `"03/04/2024"` and `"03/04/24"` are 2024-03-04, which were 2024-04-03.
  Dots, dashes, spaces and mixed separators stay day first, so
  `"03.04.2024"` is 2024-04-03. This applies to `Normalize`, `Normalized`,
  `Scan`, JSON and XML decoding, `ScanString`, `Parser`, `Finder` and
  `NullableDate`, which have no hint, so a US date read from JSON is no
  longer stored with day and month swapped. A hint only decides dates
  with slashes: `language.EN` reads them month first, every other
  language day first. Dots, dashes, spaces and mixed separators are read
  day first with every hint, so `date.Normalize("05.06.2024",
  language.EN)` is 2024-06-05, which was 2024-05-06, and an ambiguous US
  date with dashes like `"05-06-2024"` can no longer be read month first.
  A hint that can't be normalized counts as no hint in
  `ScanStringWithLang` and `Finder`, and `monthMustBeFirst` is true only
  when month first is the only valid reading.
- **Breaking:** `strfmt.NewEnglishFormatConfig` is renamed to
  `NewUSFormatConfig` and writes dates as `01/02/2006` and times as
  `01/02/2006 15:04:05 MST`, month first, which were day first, so its
  dates read back unchanged with the slash rule above.
  `NewScanConfig` accepts that time layout instead of the day first one.
- **Breaking:** `date.YearMonth`, `YearQuarter`, `NullableYearMonth` and
  `NullableYearQuarter` read and write like `date.Date` and
  `NullableDate`, see "Reading and writing values" in the README.
  - The new `Normalized` trims the surrounding whitespace and upper-cases
    the `q` of a year-quarter, which `PeriodRange` already accepted, and
    with the new `ValidAndNormalized` the four types implement
    `types.NormalizableValidator`. `Valid` and `Validate` accept every
    spelling that `Normalized` accepts, so `YearQuarter("2023-q1").Valid()`
    is true, and `Year`, `Month`, `Quarter`, `Format`, `Compare` and the
    methods built on them use the normalized value.
  - The zero values `"0001-01"`, `"0000-00"`, `"0001-Q1"` and `"0000-Q0"`
    are blank like the zero dates: `YearMonth("0001-01")` is no longer
    valid, and the nullable types are null for them and for whitespace,
    so `IsNull` is the same as `IsZero`, like for `NullableDate`.
  - The years 1 to 9999 are valid like for `Date`, which were 1 to 3000,
    so the year-month and year-quarter of every valid date can be written.
    `YearMonth.AddMonths` after `9999-12` gives the invalid `"10000-01"`,
    which `Value` refuses, instead of `""`, which it wrote as SQL NULL, and
    `YearQuarter.DateRange` of `9999-Q4` ends on `9999-12-31` instead of
    `0000-12-31`. `YearMonth.Compare` and `YearQuarter.Compare` compare
    two normalized values without normalizing them again.
  - New `Scan`, `Value`, `MarshalJSON`, `MarshalText`, `UnmarshalXML`,
    `UnmarshalXMLAttr`, `MarshalXMLAttr`, `ScanString` and `JSONSchema`,
    and `UnmarshalJSON` on `YearMonth` and `YearQuarter`. Reading stores a
    valid value normalized, a blank or zero one as the empty value or null
    and an invalid one unchanged, without an error; `Scan` reads a
    `time.Time` as its month or quarter. The nullable types read every JSON
    string unchanged before.
  - Stored values change: `Value` writes the normalized value, SQL NULL
    for a blank or zero value, and returns the error of `Normalized` for an
    invalid one. `database/sql` wrote the four types as the stored string
    by their kind, so null was written as `''` instead of NULL, and NULL
    could not be scanned into them. `MarshalJSON` writes the normalized
    value, `""` for a zero `YearMonth` or `YearQuarter` like `"0001-01"`,
    and JSON `null` for a null `NullableYearMonth` and
    `NullableYearQuarter`, which were written as `""`. `MarshalText`, used
    by `encoding/xml`, `strfmt` and the slog text handler, writes the
    normalized value or `""` for a zero one instead of the stored string,
    so `YearQuarter("2023-q1")` is written as `2023-Q1`.
- **Breaking:** the zero dates are empty in every spelling: `"0001-01-01"`,
  `"0000-00-00"`, `"01.01.0001"`, Go's zero time `"0001-01-01T00:00:00Z"`
  and the MySQL zero date-time `"0000-00-00 00:00:00"` are
  `date.Date.IsZero`, read as `""`, written as
  SQL NULL and as JSON `""` by `Date` and `null` by `NullableDate`, and are
  no valid `Date`. `Date("0001-01-01")` was valid and written as SQL NULL,
  while `Date("01.01.0001")` was written as `'0001-01-01'`. The comparison
  methods treat a zero date like an invalid date.
- **Breaking:** the address collections `email.AddressList`,
  `NullableAddressList` and `AddressSet` keep their addresses as stored in
  every format, because normalizing rewrites every entry and could merge two
  elements of a set: `{"John@Example.com", "john@example.com"}` was written
  as one address and read back as a set with one element. `Value` writes the
  stored list or addresses, trimmed, and returns an error for an invalid
  list or address. `MarshalJSON` of the lists writes the stored string, and
  of `AddressSet` a sorted JSON array, which was an object with the
  addresses as keys; `UnmarshalJSON` of `AddressSet` still reads that
  object. `Scan` and `UnmarshalJSON` of the three types read a PostgreSQL
  array, a JSON array or object, a JSON string and a plain address list.
  Normalize with `Normalized` or `AddressSet.NormalizedAddressList`.
- **Breaking:** `email.AddressList.Split` and `NullableAddressList.Split`
  are renamed to `SplitNormalized`, which says what they return, next to
  the new `SplitRaw`.
- **Breaking:** `types.Set[T]` of a normalizing string type, one that
  implements `types.Normalizable[T]`, writes and reads its values as stored
  in JSON, instead of through the normalizing `MarshalJSON` of `T` that wrote
  `Set[money.Currency]{"eur", "EUR"}` as `["EUR","EUR"]`. The JSON methods
  of other types are still used.
- **Breaking:** `email.Address.Normalized`, `email.AddressFrom` and so the
  normalization of every `email` type keep a non-ASCII display name as
  quoted UTF-8 (RFC 6532) instead of encoding it with RFC 2047:
  `Jürgen Müller <J@X.de>` and `=?utf-8?q?J=C3=BCrgen_M=C3=BCller?= <j@x.de>`
  both normalize to `"Jürgen Müller" <j@x.de>`, so normalized addresses stay
  readable in JSON and databases. The `From`, `ReplyTo`, `To`, `Cc`, `Bcc`
  and `DeliveredTo` of a message parsed by `ParseMIMEMessage` hold UTF-8
  names too. `Message.BuildRawMessage` still writes RFC 2047 encoded names,
  because MIME headers must be ASCII. ASCII names are formatted as before,
  except names containing `=?`, which are written quoted with every `=?`
  escaped as `=\?`, because the parser and Python's email package would
  decode them again: the name `=?utf-8?q?x?=` is written
  `"=\?utf-8?q?x?=" <a@b.com>` and stays that way, instead of turning into
  `"x" <a@b.com>` when normalized once more. A quoted name whose every `=?`
  is escaped is not decoded, but it is refused if Python's email package,
  which writes it again without the backslash, then reads an encoded-word
  in it that the parser can't decode or that decodes to an address or
  another encoded-word, like `"=\? x@evil.com" <ceo@corp.com>`.
  `"Really=?" <a@b.com>` normalizes to `"Really=\?" <a@b.com>`. `ASCII`
  writes a non-ASCII name with special characters in B encoded-words of at
  most 75 characters, or as one longer word where a word would hold only
  ASCII text, which Python's email package writes unencoded, so that the
  `;` of `(Vorstand; Finanzen)` ends the name.
- **Breaking:** `email` normalization keeps the content of a quoted local
  part, only lower cased, instead of removing the quotes and turning spaces
  and commas into dots: `"Doe, John"@example.com` normalizes to
  `"doe, john"@example.com` instead of the other mailbox
  `doe..john@example.com`, and `"x@evil.com>"@example.com` stays an address
  at example.com. `AddressPart`, `LocalPart`, `Message.Recipients`,
  `AddressList.UniqueAddressParts` and the headers of `BuildRawMessage`
  quote such a local part like `net/mail` does, and also where this
  package can't read it unquoted, like `"'abc"@example.com` and
  `"дмитрий"@example.com`. Escaped quotes and backslashes in a quoted local
  part, like `"a\"b"@example.com`, are read. Quoted display names are read
  with their escapes like `net/mail` reads them, and written with escaped
  quotes and backslashes like `mail.Address.String`, so
  `"Say \"Hi\"" <a@b.com>` stays as it is, and a list like
  `"x\" <ok@example.com>, ok2@example.com (," <other@example.net>` parses
  as the recipients that `net/mail` and a mail server read. Display names
  lose the runes that are not graphic, like bidi overrides decoded from
  RFC 2047. Names of RFC 2047 encoded-words keep the quotes and backslashes
  of their text, and `ASCII` B-encodes a non-ASCII name with a backslash. A local part with
  consecutive, leading or trailing dots, like the `doe..john@example.com`
  that earlier versions made of `"Doe, John"@example.com`, is now written
  quoted as `"doe..john"@example.com`: normalize stored columns again
  before comparing them with values written by this version.
- **Breaking:** `email.ParseAddressList` reads only a whole placeholder,
  like `undisclosed-recipients` or `undisclosed-recipients:;`, as a list
  without addresses, instead of every list starting with one. The address
  `undisclosed-recipients@example.com` and the name in
  `withheld recipients <victim@example.com>` are read as such, and text
  after a placeholder, like `undisclosed-recipients:;, victim@example.com`,
  is parsed, so `Validate` rejects that list instead of accepting it as
  empty while other parsers read the address in it.
- **Breaking:** `money.Currency.Normalized` guesses EUR only from the words
  `EUR`, `Euro` and `Euros`, like the other units, instead of from any text
  containing `EUR`, so `TEUR` (thousands of euros) and `Amateur` are no
  currencies. Only text of letters, spaces and `.`, `-`, `(` and `)` is
  guessed, so `USD 1.5`, `€ USD` and `100 Dollars` are no currencies.
- **Breaking:** `bank.BIC.Validate` and `Valid`, and so `NullableBIC`,
  `StringIsBIC` and `BIC.ScanString` with `validate`, remove whitespace like
  `Normalized`, so `"BKAU AT WW"` is valid, and `BIC.ScanString` stores the
  normalized BIC like the other `ScanString` methods. `CountryCode`, `IsTestBIC`,
  `IsPassiveSWIFT` and `ReceiverPaysFees` read the normalized BIC.
  `BIC.Parse` and `BICParser` still reject whitespace.
- **Breaking:** the interface `types.ValidatErr` is renamed to
  `types.Validatable`, together with its helpers: `ValidatErrFunc` to
  `ValidatableFunc`, `StaticValidatErr` to `StaticValidatable`, `ValidatErrs`
  to `Validatables`, `CombinedValidatErr` to `CombinedValidatable` and
  `ValidatorAsValidatErr` to `ValidatorAsValidatable`.
- **Breaking:** `types.TryValidate` returns the error last, as
  `(implemented bool, err error)`, which was `(err error, isValidatable bool)`:
  `err, ok := types.TryValidate(v)` becomes `ok, err := types.TryValidate(v)`.
- **Breaking:** `types.Validatables.Validate` and so `types.CombinedValidatable`
  validate every element and return all their errors joined with `errors.Join`,
  instead of stopping at the first error and returning it. A single error is
  now wrapped by the join as well, so compare with `errors.Is` instead of `==`.
  An element after a failed one is called too, so an element that relies on
  an earlier one, like a field check after a check that the pointer to the
  struct is not nil, has to become one `Validatable` with that check.
- **Breaking:** the `money` currency constants (`EUR`, `USD`, …) are typed
  `Currency` instead of untyped strings, so go-enum can collect them.
  Assigning one to a `string` or `NullableCurrency` now needs a conversion:
  `string(money.EUR)` or `money.EUR.NullableCurrency()`.
- `uu.ID.V7Time` now returns a second `ok bool` result reporting whether the
  UUID is a version 7 UUID. Callers no longer have to compare the returned
  time against the zero time to detect that there was no timestamp to decode.
- Removed `money.NewAmount`, `money.NewRate` and `money.NewDecimalAmount`'s
  pointer form. They only allocated a pointer to a converted value, which
  Go 1.26's `new(expr)` expresses inline: `new(money.Amount(1.23))` and
  `new(money.NewDecimalAmount(1999, 2))`. `AmountFromPtr`/`RateFromPtr` and the
  `Ptr` methods are unchanged.
  `money.NewDecimalAmount(coefficient, scale)` keeps its name and still returns
  a `DecimalAmount` value. The package convention is now uniform: a `New*`
  function does real work and returns a value. The two `New*Parser` functions
  keep returning pointers because their `Parse` methods have pointer receivers.
- `money.Amount.GoString` now returns a Go source representation
  (`money.Amount(0.5)`) instead of a bare number, and uses enough fractional
  digits for the exact decimal expansion of every `float64`. The previous
  200-digit format silently printed subnormals and any value below roughly
  `1e-200` as `0`. Non-finite values and negative zero render as
  `money.Amount(math.NaN())`, `money.Amount(math.Inf(1))` and
  `money.Amount(math.Copysign(0, -1))` so the output always parses back to the
  identical amount.
- `money.ParseDecimalAmount` accepts scientific notation like `1.5e2` instead
  of rejecting it. The exponent shifts the scale of the exactly parsed
  coefficient, so no precision is lost on the way. This makes
  `DecimalAmount.UnmarshalJSON` accept the exponent form that JSON encoders
  emit for `float64` values outside `1e-6`..`1e21`, and `DecimalAmount.Scan`
  accept the exponent form PostgreSQL uses in `float8` text output. The
  resulting scale still has to fit `MaxDecimalAmountScale`, so `1e-19` is an
  error while `10e-19` (== `1e-18`) is not, and `acceptedDecimals` is now
  matched against the scale of the result rather than the decimals written in
  the mantissa. That last point diverges from `ParseAmount`, which keeps
  matching the decimals written in the string: for `"1.5e2"`
  `ParseDecimalAmount` accepts `0` and `ParseAmount` accepts `1`.
  Redundant trailing zeros of the mantissa are dropped when, and only when, the

  nil string sets null. `strfmt` formatted these types but returned
  `can't scan "1,5" as destination type nullable.Type[...]` for them. A
  non-null `nullable.Type[T]` without a registered formatter is formatted
  like its `T` instead of as `{1234 true}`.

### Removed

- **Breaking:** `types.Ptr` and `strutil.Ptr`. Since Go 1.26, the minimum
  Go version of this module, the built-in `new` accepts a value:
  replace `types.Ptr(x)` and `strutil.Ptr(s)` with `new(x)` and `new(s)`.
- **Breaking:** `strfmt.FormatConfig.Percent`. The field was set by the
  presets but never read anywhere.
- **Breaking:** `types.ErrInvalidValue`. `types.Validate`, `TryValidate`,
  `DeepValidate` and `ValidatorAsValidatable.Validate` return an error naming
  the type and value for a `Validator` whose `Valid()` is false, like
  `invalid main.Status value: "unknown"`, instead of the bare `invalid value`.
  Any non-nil error means the value is invalid. The error of a `Validatable`
  is still returned unchanged; it never wrapped `ErrInvalidValue`, so
  `errors.Is(err, ErrInvalidValue)` was never a reliable invalidity check.
- **Breaking:** the set methods deprecated in the 2026-09-02 release. Each
  removal is a compile error at the call site:

  | Removed                 | Replacement                               |
  |-------------------------|-------------------------------------------|
  | `Add(v)`¹               | `Insert(v) bool`                          |
  | `AddSlice(s)`           | `InsertAll(slices.Values(s))`             |
  | `AddSet(other)`¹        | `UnionWith(other)`                        |
  | `DeleteSlice(s)`        | `DeleteAll(slices.Values(s))`             |
  | `DeleteSet(other)`      | `DifferenceWith(other)`                   |
  | `IDSet.AddIDs(ids)`     | `InsertAll(slices.Values(ids.AsSlice()))` |
  | `IDSet.AsSortedSlice()` | `Sorted()`                                |

  ¹ Removed from `types.Set`, `uu.IDSet` and `strutil.StringSet` only.
  `email.AddressSet` keeps its nil-safe pointer-receiver `Add` and `AddSet`;
  only its `DeleteSlice` and `DeleteSet` are removed.

- **Breaking:** `bank.AccountType`, `bank.TransactionType` and
  `bank.PaymentStatus`, along with `AccountType`'s `Valid`, `Scan` and `Value`
  methods. The three types had no callers in this module, and only
  `AccountType` carried any behaviour at all: `TransactionType` and
  `PaymentStatus` declared their constants and nothing else, so neither could
  round-trip through SQL. Declare the enum you need in the consuming service,
  or ask for them back as generated `//#enum` types.

- **Breaking:** `money.BTC` and the `₿` symbol mapping. Bitcoin is not an
  ISO 4217 currency, and the constant was never valid: `Valid()` resolves
  through `currencyCodeToName`, which has had no `BTC` entry since the initial
  commit, so `money.BTC.Valid()` always returned `false`. The symbol was the
  only input that reached it, which made `Currency("₿").Valid()` true while
  `money.BTC.Valid()` was false. `Currency("₿")` no longer normalizes.

- **Breaking:** `email.NullableAddress.UnmarshalText`, so `NullableAddress`
  no longer implements `encoding.TextUnmarshaler`. The Go 1.26
  `encoding/json` decodes a map key whose type has `UnmarshalText` through
  its `UnmarshalJSON`, which now normalizes, so two spellings of an address
  merged into one key of a `map[NullableAddress]V`. Like `Address` and the
  other normalizing types, a `NullableAddress` map key, `,chardata` field or
  value of a decoder that sets strings directly is read as given.
  `flag.TextVar` no longer accepts a `*NullableAddress`.

### Fixed

- `date.Date.ValidAndNormalized` was true for the year 0, like for
  `"0000-01-01"`, which `Valid` rejects.
- `account.NullableNumber.String` returned a null of whitespace or control
  characters unchanged instead of `""`.
- `uu.NullableIDMust` panicked for the Nil UUID passed as `uu.ID` instead of
  returning `IDNull` like for the other argument types.

- `email.AddressList.Value`, `NullableAddressList.Value`,
  `AddressSet.Value` and `AddressSet.MarshalText` wrote text with runes
  that the address parser ignores when it validates: control characters
  other than the tab, like CR, LF and NUL, bidi embeddings, overrides and
  isolates (U+202A to U+202E, U+2066 to U+2069), and invalid UTF-8. A
  display name like `"x\r\nBcc: evil@example.com" <a@example.com>` was
  written with its line break, which a header built from the stored list
  would turn into a header injection, and a NUL failed in PostgreSQL. They
  return an error now, and `Validate` and `Valid` of the three types refuse
  the same runes, so a validated list can be saved; store `Normalized()`
  instead. Names with a no-break space, ideographic space, zero width
  (non-)joiner, soft hyphen or directional mark are written as stored.
  In an address part, and in the spaces around it, the three types refuse
  every rune that the parser drops or reads as another rune: a rune that
  is not graphic like the soft hyphen in `ad<U+00AD>min@corp.com`, a space
  other than U+0020 like the no-break space in `x <<U+00A0>a@b.com>`, a tab
  in a quoted local part, and an apostrophe right before or after the
  address part like in `'ceo@corp.com`. The parser read these as
  `admin@corp.com`, `a@b.com` and `ceo@corp.com`, while `net/mail` and
  mail servers read other mailboxes. `AddressSet.MarshalText` also refuses
  a set whose joined list would read back as other entries, like a valid
  address with an unclosed angle bracket, `Doe <doe@example.com`, that
  swallowed the entries after it.
- `float.FormatDef.Format` and `Parse` panicked for a zero `DecimalSep`,
  as in the zero `FormatDef` or one decoded from `{"decimalSep":""}`; they
  use `.` for it. `UnmarshalJSON` rejects a zero `decimalSep` together with
  `.` as `thousandsSep`.
- `email.ParseAddressList`, and so the `Validate`, `Normalized` and `Split`
  methods of the address lists and `ParseMIMEMessage`, took quadratic time
  and memory for a list of unparsable entries: every error held the whole
  list, so 10,000 entries took seconds and hundreds of megabytes. Errors
  hold at most 100 bytes of the input, parsing stops after 100 errors, and
  each entry is parsed only up to its end, so 1 MB of entries without `@`
  or of commas takes 14 ms instead of over 6 s. A repeated address like in
  `<a@x.com> <a@x.com>` is read in a loop instead of one recursion per
  address, which exhausted the goroutine stack for millions of them.
- `email.ParseAddressList` parsed lists without an error as other entries
  than `SplitAddressList` found, so a validated list read back as other
  recipients through `AddressSet.Scan` and `SplitRaw`: an unclosed quote or
  angle bracket before a comma, like `"Doe <a@b.cc>, z@y.zz`, a stray quote
  in an unquoted name, and a leading or doubled comma, which became the
  display name `","`. These are errors now. `SplitAddressList` reads the
  placeholder `undisclosed-recipients:;,` as the empty list and splits the
  list as the parser reads it, so a backslash that escapes a rune the
  parser drops can't escape the next quote. After an invalid entry,
  parsing continues where `SplitAddressList` ends that entry, so every
  address is returned at most once, and of an entry that can't be parsed
  only the last part with the angle brackets is parsed once more, so
  `Doe, John (john@corp) <j@x.com>` still gives `j@x.com` with an error.
- **Breaking:** `email.ParseAddress`, and so `Validate` and `Normalized` of
  `Address`, `NullableAddress`, `AddressList`, `NullableAddressList` and
  `AddressSet`, refuse addresses that other parsers read as other
  recipients. Python's `email.utils.getaddresses(strict=True)`, which
  `smtplib.send_message` uses, and `net/mail` read other recipients in
  lists that validated, which are refused now:
  - an address inside a quote or comment that isn't closed:
    `"x@evil.com" "<ceo@corp.com>` validated as `ceo@corp.com` where Python
    reads `x@evil.com`, and in `Doe (Sales <doe@example.com>` Python reads
    `Doe`, so an unclosed quote or comment is an error also without a
    comma after it, and its address is not returned;
  - an `@` in an unquoted display name, unless the name is the address
    itself as written:
    `x@evil.com <ceo@corp.com>` and
    `=?utf-8?q?spy@evil.example?= <ceo@corp.example>`. An encoded-word is
    read like any other word of an unquoted name, so its unencoded comma
    separates entries like in `net/mail`;
  - a second, different address in angle brackets: `Normalized` of
    `<x@evil.com> <ceo@corp.com>` returned `ceo@corp.com`; only the same
    address may repeat;
  - a quoted name without angle brackets after it:
    `"x@evil.com" ceo@corp.com`;
  - a name with a quoted `@`, or an RFC 2047 encoded-word whose text holds
    an `@` or `=?`, followed by one of `;:)>[]\,`, which Python's lenient
    parser and its default header parser, the one `EmailMessage` and
    `smtplib.send_message` use, also send to that address:
    `"x@evil.com"; <ceo@corp.com>`, `Team:"x@evil.com":<ceo@corp.com>` and
    `=?utf-8?q?=C3=A4_x=40evil.com?=; <ceo@corp.com>`, and with a backslash
    also before it: `\"x@evil.com" <ceo@corp.com>`. One of them before
    such an address only ends the name, so
    `Doe; =?utf-8?q?J=C3=BCrgen?= <ceo@corp.com>` stays valid;
  - an RFC 2047 encoded-word at the start of a word whose decoded text is
    ASCII and contains one of `"<\`, an `@` or `(` outside a comment that
    it closes, a comment and one of `;:)>[],`, or an `=?` at the start of
    a word, also inside a quoted name, because Python writes it back
    unencoded: `=?utf-8?q?x=40evil.com?= <ceo@corp.com>`; an `=?` at the
    start of a word of the decoded name, which Python decodes once it
    wrote the name: `=?utf-8?b?PT8=?=utf-8?q?x <y?=@corp.com>`; a quoted
    name with an escaped `=\?` that holds such an encoded-word once Python
    wrote it again without the backslash:
    `"=\?utf-8?q?x" <y?=@corp.com>, "<evil@evil.com>" <c@corp.com>` was
    sent to `evil@evil.com`; an `=?` at the start of a word that the
    parser can't decode, like one with an unknown charset or invalid
    encoding, which Python decodes anyway, also up to a `?=` after the
    name; and `=?` at the start of a local part or after a space or dot in
    it, which Python decodes: `=?utf-8?q?admin?=@corp.com`. Encoded-words
    with non-ASCII text stay valid, because Python encodes them again, and
    so do ASCII words with other specials, which only end the name for
    Python, like the last of the two words a mail client writes for
    `Jürgen Müller, Buchhaltung und Finanzen (Abteilung Nord)`, ASCII words
    with a closed comment, like the `und Buchhaltung (Zentrale)` that
    `net/mail` and Python's `email.header` split off a long name, and an `=?`
    within a word, like in `"Really=?" <a@b.com>`;
  Quote such names: `"x@evil.com" <ceo@corp.com>` is valid.
  `ParseMIMEMessage` reports such an address header as an error and keeps
  the addresses it can parse, so `From: x@evil.com <ceo@corp.com>` leaves
  `From` empty, also for such an encoded-word. `ParseAddressList` and the
  `SplitNormalized` methods never
  return an address from inside a quoted string or comment: for
  `Support, "x\" <ceo@corp.com>, y (," <attacker@evil.com>` they returned
  `ceo@corp.com` and now return `attacker@evil.com` with an error. The
  collections also refuse runes the parser drops in an unquoted name that
  is the address, in a repeated address, and after a comment after an
  address up to the next comma, where Python appends them to the domain.
- `email` local parts are lower cased without turning a non-ASCII rune
  into ASCII: `"<U+212A>ate"@corp.com`, with the Kelvin sign, was read as
  `kate@corp.com`. The domain of an unquoted name that equals the address
  is compared the same way. An address without a name whose quoted local
  part holds a `<` is written in angle brackets, so `Normalized` reads it
  back as the same address. A run of empty entries in an address list is
  one error, and parsing continues after it, so 1 MB of commas before an
  entry with angle brackets takes milliseconds instead of 6 s.
- `email.AddressList`, `NullableAddressList` and `AddressSet` store an
  unquoted display name as written, which is a known risk: some mail
  stacks read its words as recipients. Python's `EmailMessage` with
  `smtplib.send_message` sends `admin, John <ceo@corp.com>` to `admin` and
  `ceo@corp.com`, and `John Doe [External] <ceo@corp.com>` only to
  `John Doe`. Store `Normalized()`, which quotes every name, or quote the
  name where the text goes into a header of another system.
- **Breaking:** the domain of an email address may not have an empty
  label: `e@f.net..Doe` was valid and normalized to `e@f.net..doe`, which
  `net/mail` rejects. `AddressRegexp` and `FindAllAddresses` match no domain
  with consecutive dots either.
- `email.AddressList.Validate` accepted a list that `Value` refused when a
  backslash preceded a rune at the end that `strutil.TrimSpace` removes;
  both refuse it now.
- `date.YearQuarter.AddQuarters` and `NullableYearQuarter.AddQuarters`
  looped once per year, so a large count from input took about 400 ms for
  `1<<32` and never returned for `math.MaxInt`. They compute the year by
  division without overflow; a result past `9999-Q4` or before the year 1
  stays invalid, so `Value` refuses it.
- `email.ParseAddress` and `ParseAddressList`, and so the `Validate` and

  b@example.com`. A nested comment stays in the name, so
  `mike@doe.com (Mike (Sales))` normalizes to
  `"Mike (Sales)" <mike@doe.com>`. A comma inside a comment no longer
  separates addresses, `a@example.com (outer (inner, x)), b@example.com`
  is valid, and a comment that isn't closed is an error:
  `a@example.com (x (y)` was valid with the name `x (y`, and in a list it
  holds the rest of the list, so parsing stops there with an error.
- `email.Address` and `NullableAddress` built an error with a call stack
  for every invalid value they read or write unchanged, which `Scan`,
  `UnmarshalJSON`, `UnmarshalXML`, `MarshalJSON` and `MarshalText` dropped;
  `Scan` of an invalid address is about twice as fast and allocates
  nothing. Each `ParseAddressList` error carries one call stack instead of
  two.
- `email.ParseAddress` read `attacker@evil.com ceo@corp.com` as
  `ceo@corp.com`, which `net/mail` rejects. A repeated address is only
  read from angle brackets, and only the same address may repeat.
- `date.Normalize` accepted the year 0 in the year-day-month order, like
  `"0000 25 may"`, which `Scan` and PostgreSQL reject.
- `date.Date.Format` and `NullableDate.Format` formatted an invalid date as
  the zero time, like `"01.01.0001"`, with every layout but `Layout`, and so
  did `strfmt`. An invalid date is returned unchanged.
- `types.Validate`, `TryValidate`, `DeepValidate`, `Validators.Valid` and
  `ValidatorAsValidatable.Validate` panicked for a struct that embeds a nil
  `*T` whose `T` implements the method with a value receiver, or a nil
  interface like `types.Validatable` or `types.Validator`. Such a value is
  not validated, like a nil pointer. A nil pointer dereference in a method
  that the struct declares itself still panics instead of reporting the
  value as valid.
- `float.FormatDef.UnmarshalJSON` accepted separators and precisions that
  `Format` panics on, like `{"decimalSep":"."}` into a `FormatDef` with `.`
  as thousands separator, which gave the same rune for both, or a precision
  below -1.
- `float.Parse` read the price notation `"12,-"`, 12 without cents, as -12.
  A `-` right after the decimal separator is no sign.
- `bank.BIC` accepted the false BICs of 8 characters with the `XXX` branch

- `charset.DecodeUTF16` and `EncodeUTF16` panicked for a nil

  addresses, so an encoded comma and `@` in a display name, like in

  with an error; a name in a comment that can't be decoded is dropped. A

  `a@example.com (=?utf-8?q?M=C3=BCller?=)` is decoded.

  amount now goes to the last part like for all other amounts.

  whitespace, so a padded `{...}` was stored as the literal text.

- `notnull.JSON(nil).Clone()` returned a non-nil empty value that marshalled
  to zero bytes, which is not valid JSON. It now returns nil.
- `money.StringIsAmount` and `money.AmountFinder` matched the `NaN` and `Inf`
  tokens anywhere in a string, so `StringIsAmount("Information", false)` was
  true. The tokens now have to be the whole string.
- `money.Rate.ScanString` rejected a trailing percent sign, `"15%"`, which
  `ParseRate` and `Rate.UnmarshalJSON` accept as 0.15.
- `float.Format` grouped thousands by the digits before rounding, so
  `999.995` with two decimals and a comma separator was `"1000.00"` instead
  of `"1,000.00"`.
- `float.ParseDetails` read `"1,234,567e3"` as 1234567, dropping the
  exponent after a grouped number.
- `strfmt` formatted `float32` values with float64 precision, so
  `float32(0.1)` was `"0.10000000149011612"` instead of `"0.1"`.
- `strfmt.ScanConfig.SetTypeScanner` panicked on a `ScanConfig` not created
  with `NewScanConfig`.
- `types.Validate` and `types.TryValidate` panicked for a nil
  `types.ValidatorFunc` or `ValidatableFunc`, and `types.Validatables` and
  `types.Validators` for a nil element, and `types.ValidatorAsValidatable`
  for a nil `Validator`. Nil funcs and elements are now skipped like in
  `DeepValidate`.
- `types.CanMarshalJSON` reported true for a map whose key type only
  implements `encoding.TextMarshaler` through its pointer type, which
  `json.Marshal` rejects.
- `uu.IDSlice` and `uu.IDSet` rejected a JSON array with only whitespace
  between the brackets, like `[ ]`.
- `nullable.IntArray` and `nullable.FloatArray` named the `notnull` types in
  their scan errors.
- `date.Date.IsToday` and `IsTodayInUTC` compared the raw string with today's
  date, so a valid date in another format was never today.
- `date.Date.Scan` and `NullableDate.Scan` rejected a `[]byte`, which some
  SQL drivers return for `date` and `text` columns.
- `bank.NullableIBAN.CountryCode` sliced the raw string, so an IBAN with
  leading whitespace returned `" D"` instead of `"DE"`.
- `email.NullableAddress.Scan` rejected a `[]byte`, which `AddressList` and
  `NullableAddressList` accept.
- `account.NullableNumber.UnmarshalJSON` rejected the JSON string `""`, which
  `Scan` and `UnmarshalText` read as `NumberNull`.
- `date.Finder` did not find ISO 8601 date-times like
  `2023-12-25T10:00:00Z`, which `date.Normalize` accepts, because it lower
  cased the candidates before checking them for the `T`.
- `date` parsing only knew the French, Italian and Spanish names of January,
  so `"2 févr. 2019"` or `"5 luglio 2021"` did not parse. Every month name
  and its usual abbreviation is now known. `date.Finder` reads the
  abbreviations that are common words in other languages, `set`, `ago`,
  `mag`, `lug`, `ott` and `dic`, only with `language.IT` or `language.ES`
  as hint, so text like `"Game set 10 2020"` has no date.
- `money.Amount.UnmarshalJSON` and `money.Rate.UnmarshalJSON` stripped the
  quotes of a JSON string without decoding its escapes, so `"1\u002c5"`
  failed while `float.Tolerant` and `DecimalAmount` decode it as 1.5.
- `date` parsing stripped the ordinal suffix `st` from the month name
  `august`, so `"17 August 2012"`, `"August 17, 2012"`, `"1. August 2016"`
  and `"1st August 2020"` were invalid and `date.Finder` skipped them.
- `date.Date.MidnightUTC`, `Midnight` and `MidnightInLocation`, and those of
  `NullableDate`, return the zero time or null for a year 0 date like
  `"0000-01-01"`, which `Valid` rejects. They returned midnight of year 0.
- `date.NullableDate.Format(date.Layout)` returns `""` for every null date
  like the other layouts do. It returned the raw `"0001-01-01"`,
  `"0000-00-00"` or whitespace.
- `charset.DecodeUTF16`, `DecodeUTF16String` and the decoder of
  `UTF16Encoding` rejected UTF-16 text starting with the bytes `EF BB BF` as
  having a UTF-8 BOM, although they are valid UTF-16 like U+BBEF in
  UTF-16LE, so the `EncodeUTF16` round trip of such text failed.
- `charset.DecodeUTF32`, `DecodeUTF32String` and the decoder of
  `UTF32Encoding` rejected UTF-32LE text starting with the bytes `FF FE` as
  having a UTF-16LE BOM, although they are valid UTF-32LE like U+FFEFF. A
  BOM of another encoding is only rejected if its bytes are no valid UTF-32
  character.
- `float.ParseDetails` reported `'.'` as the decimal separator of a number
  with an exponent like `"1,5e3"` instead of the `','` of the input.
- `encoding/xml` panicked for a nil pointer attribute field of `uu.ID`,
  `uu.NullableID`, `uu.IDSet`, `uu.IDSlice`, `notnull.TrimmedString`,
  `nullable.TrimmedString`, `nullable.Time` and `money.DecimalAmount`
  without `omitempty`, like `ID *uu.ID` with the tag `xml:"id,attr"`,
  because it called their value receiver `MarshalText` through the nil
  pointer. A pointer receiver `MarshalXMLAttr` leaves such an attribute out
  and writes a non-nil one like `MarshalText`, as for the normalizing types.

## 2026-09-02

### Added

- `strfmt.ScanConfig.StrictEmptyStringParsing` controls what a nil source
  string means for a destination that can neither hold nil, be set to null,
  nor hold the source string itself, like a number, a bool or `time.Time`.
  When `false` (the default) such a destination is assigned its zero value,
  so a spreadsheet row with empty cells stays scannable into a column of any
  type. When `true` it is an error, unless the type has a `ScanString` or
  `UnmarshalText` method that gives a nil source string its own meaning.
- `strfmt.Scan` sets a destination with a `SetNull()` method to null for a
  nil source string, so every nullable type behaves the same way for an
  empty cell without its scanning method having to repeat it.
- `strfmt.Scan` supports multiple levels of pointer indirection.
- A `nullable.Time` scanner is registered by default in `strfmt.NewScanConfig`,
  so it parses every configured `TimeFormats` layout instead of only the
  RFC 3339 format that its `UnmarshalText` method accepts.
- `strfmt.Scan` accepts a `time.Duration` without a unit suffix as plain
  nanoseconds, which is how a duration is represented by its underlying
  `int64` kind and how it is marshalled as JSON.

- **`mapset` package** — set operations on `map[K]struct{}` and `map[K]bool`,
  mirroring the `container/mapset` package proposed for Go 1.28
  ([go.dev/issue/77052](https://go.dev/issue/77052), CL 724420) function for
  function. It is the shared implementation behind the set methods of
  `types.Set[T]`, `uu.IDSet`, `strutil.StringSet` and `email.AddressSet`, and
  can be replaced by the standard library package with an import path change
  once Go 1.28 ships.
- The methods of the abstract set interface of the Go collections proposal
  ([go.dev/issue/80590](https://go.dev/issue/80590)) on all four set types:
  `All`, `ContainsAll`, `DeleteAll`, `DeleteFunc`, `Difference`,
  `DifferenceWith`, `Insert`, `InsertAll`, `Intersection`, `IntersectionWith`,
  `Intersects`, `SymmetricDifference`, `SymmetricDifferenceWith`, `Union` and
  `UnionWith`. They now behave like the `container/set.Set` type planned for
  Go 1.28, which is likewise represented as `map[E]struct{}`.
- `strutil.StringSet.Len` and `email.AddressSet.Equal`, which were missing.
- `ContainsAny` on `uu.IDSet` and `email.AddressSet`, `IsEmpty` on
  `strutil.StringSet` and `Sorted` on `uu.IDSet`, so that all four set types
  now offer `ContainsAny`, `ContainsAll`, `IsEmpty`, `Len` and `Sorted` under
  the same names. `strutil.StringSet` still has no `IsNull`, being the one
  set type that does not distinguish a nil from an empty set.
- `internal/collections` holding the proposal's abstract interfaces, and
  `internal/collections/settest` holding the abstract set specification as a
  reusable test. Every set type is checked against that specification and by a
  compile-time interface assertion, so a behaviour change in `mapset` is caught
  at each type that delegates to it, not only in `mapset` itself.
- `nullable.SplitArrayValues` and `notnull.SplitArrayValues`, which split an
  SQL or JSON array into its top level elements like `SplitArray` and return
  the value of every double quoted string element with the quotes removed and
  the escape sequences of the parsed syntax undone. `SplitArray` returns the
  raw text of its elements, which is required for a JSON array of objects but
  is the wrong thing for a string array, and because it was the only thing on
  offer every known caller hand-rolled the unquoting and got it wrong. SQL and
  JSON unescape differently — a backslash escapes the following character
  whatever it is in a PostgreSQL array literal, while JSON interprets `\n`,
  `\t` and `\uXXXX` — so the new functions unescape with the syntax they
  parsed, and a PostgreSQL element is unescaped whether it is quoted or not.
  Elements that are not double quoted strings, like the objects of a JSON array
  of objects, are returned unchanged. A quoted element of a JSON array that is
  not a valid JSON string is an error, because returning it unchanged would
  hand out the value with the quotes these functions exist to remove, which is
  not distinguishable from a value that really has them.

### Fixed

- `strfmt.FormatValue` returned the text of `encoding.TextMarshaler` only when
  `MarshalText` returned an **error**, and fell through to the generic
  conversions when it succeeded. The condition was inverted; a successfully
  marshalled text is now used, as the documentation always stated.
- `strfmt.Scan` silently truncated an integer that did not fit the destination
  type: `"300"` scanned into an `int8` assigned `44`. Integers are now parsed
  with the bit size of the destination type, and floats are range checked, so
  both report an out-of-range value as an error.
- `strfmt.Scan` panicked inside the `reflect` package for a destination that is
  invalid or not settable, like the value of an unexported struct field. Those
  are reported as errors now. A pointer that is not settable itself, like
  `reflect.ValueOf(&x)`, is scanned by scanning the value it points to.
- `strfmt.Scan` replaced an already allocated pointer destination with a newly
  allocated value, silently dropping every field the scanning method did not
  assign and leaving other holders of the original pointer with a stale value.
  An allocated pointer is now scanned in place and keeps its identity.
- `strfmt.Scan` could leave a destination partially assigned when it returned
  an error, because a scanning method can assign before it fails and
  `ValidateFunc` runs after the value was assigned. A failed scan no longer
  modifies the destination at all.
- `strfmt.Scan` used the scanner registered for a type only for the type
  itself, so a `*time.Time` destination fell through to the RFC 3339 only
  `UnmarshalText` method of `time.Time`. A pointer destination now parses the
  same strings as its value equivalent.
- `strfmt.FormatValue` panicked in `reflect.Value.Interface` for the value of
  an unexported struct field. An addressable one is now formatted like an
  exported field, so a reflection driven caller walking a struct gets
  `2026-01-02T15:04:05Z` instead of a crash or `{0 63902963045 <nil>}`.
- `email.AddressSet`, `email.AddressList` and `email.NullableAddressList` kept
  the quotes of a quoted PostgreSQL array element, so scanning the `{"a@x.com"}`
  literal that `AddressSet.Value` itself writes produced the address
  `"a@x.com"` including the quote characters and `Value` did not survive `Scan`.
  All three now decode the array with the same PostgreSQL array codec that
  `Value` writes with, which also unescapes an element containing a comma or an
  escaped quote. An SQL `NULL` array element is an error now instead of the
  address `NULL`.

  Two deliberate limits of that decoding: every element is trimmed, so a member
  stored with leading or trailing whitespace (which `Validate` rejects anyway)
  does not survive a `Value`/`Scan` round trip, and an element that is empty
  after trimming is dropped. The trim is what keeps a hand-written literal like
  `{ a@x.com , b@x.com }` working, which the previous decoder accepted.
- **Breaking:** `nullable.SQLArrayLiteral` and `notnull.SQLArrayLiteral` escaped
  the quote but not the backslash of an element, so the literal `{"a\b"}`
  written for the value `a\b` is read back by PostgreSQL as `ab`: a silent data
  loss for every value containing a backslash. Both characters are escaped now,
  and a test pins the literal to be byte identical to the one written by the
  vendored `pq.StringArray.Value` and to round trip back through its parser. The
  literal was additionally checked against a live PostgreSQL 16 during
  development, which the test suite itself does not do, having no database.
  Nothing about the changed output produces a compile error: review stored
  literals, golden tests and anything comparing the output. A caller that pairs
  `SQLArrayLiteral` with `SplitArray` and strips the quotes itself has to move
  to `SplitArrayValues` now: the literal written for `a\b` is `{"a\\b"}`
  instead of `{"a\b"}`, so stripping only the quotes yields `a\\b`. It fails
  silently, which is the same trap that made this function worth fixing.
- **Breaking:** `SplitArray` reported an unclosed quote for a quoted element
  whose value ends with a backslash, like the `{"a\\"}` literal PostgreSQL
  outputs for the value `a\`, because it took the escaped backslash before the
  closing quote for an escape of that quote. Escape sequences are tracked now
  instead of looking at the previous character only. The tracking cuts the other
  way for a malformed literal that PostgreSQL never emits: `{"a\\"","b"}` used
  to split into two elements and is an `invalid rune` error now, which is what
  PostgreSQL reports for it too.
- **Breaking:** the `SplitArray` functions honoured the backslash escaping of a
  PostgreSQL array literal in a quoted element only, so the literal `{a\,b}`,
  which PostgreSQL reads as the single value `a,b`, was split into the two
  elements `a\` and `b`. A backslash escapes the following character in an
  unquoted element too, verified against PostgreSQL 16, and is now undone by
  `SplitArrayValues` for every element of an SQL array. Note that the vendored
  `lib/pq` parser behind `StringArray.Scan` implements the escaping for quoted
  elements only, so it still reads `{a\,b}` as two elements; `SplitArrayValues`
  follows PostgreSQL, not `lib/pq`. A JSON array is unaffected, a backslash
  outside a quoted string is not JSON syntax.
- **Breaking:** the `SplitArray` functions dropped the last element of a literal
  with a trailing comma: `{a,}` returned `{"a"}` and lost the element the comma
  announced without reporting anything. That comma now yields an empty string as
  last element. PostgreSQL rejects the literal outright, this parser is the
  tolerant one and reports what it read rather than silently returning a shorter
  array. An empty element between two commas, `{a,,b}`, stays an error.
- The `SplitArray` functions counted the `{`, `[`, `}` and `]` of a nested
  object or array without noticing that those runes can appear inside a string
  value of it, so a JSON array of objects failed to split with a `has too many
  '}'` error as soon as one of its string values contained a closing brace or
  bracket, like `[{"a":"}"}]`. Nesting deeper than one level failed the same
  way, because only the opening rune of an element was counted and never the
  ones within it, so `[{"a":{"b":1}}]` and `[[1,[2]]]` were rejected too. Both
  are tracked now, like the escapes of a quoted element. Every well-formed
  literal that split before splits into the same elements; only malformed input
  whose braces happened to balance out, like `[{a{b}]`, is an error now. An
  unmatched `{` or `[` at the top level of an unquoted element stays literal
  text, so a hand written `{in{o@example.com}` still parses.
- The `SplitArray` functions could not tell the value of a quoted string
  element, which is what `SplitArrayValues` was added for. Their documentation
  now says so, and also that an unquoted `NULL` element of an SQL array (`null`
  in a JSON array) is returned as the string `NULL` (`null`) and is
  indistinguishable from a quoted `"NULL"` (`"null"`) element for
  `SplitArrayValues`. `SplitArray` keeps the quotes that tell the two apart and
  its elements correspond to those of `SplitArrayValues` by index.

### Changed

- `strfmt.Scan` resolves a nil source string (as reported by `ScanConfig.IsNil`,
  now compared with surrounding whitespace trimmed) before dispatching to a
  `Scannable` or `encoding.TextUnmarshaler` destination, so that every type gets
  the same handling instead of every scanning method repeating it. A `Scanner`
  registered in `ScanConfig.TypeScanners` keeps taking precedence over all
  built-in scanning logic, including this handling, so it can give a nil source
  string a meaning of its own. The scanners registered by `NewScanConfig` apply
  the standard handling themselves.
- **Breaking:** with the default `StrictEmptyStringParsing == false`, scanning
  an empty or `"NULL"` cell into a number, a bool, `time.Time` or a
  `Scannable` type such as `money.Amount` assigns the zero value instead of
  returning a parse error. Set `StrictEmptyStringParsing = true` to restore the
  previous behavior.
- **Breaking:** `strfmt.FormatValue` now prefers `encoding.TextMarshaler` over
  the conversions based on the value's kind, as documented. Types with a
  registered `FormatConfig.TypeFormatters` entry are unaffected, since those
  are still resolved first. Observable for `notnull.TrimmedString` and
  `nullable.TrimmedString`, which now format their normalized text.
- A value assigned for a nil source string is not passed to
  `ScanConfig.ValidateFunc`, because the absence of a value is not a value to
  validate. A `string` destination assigned the source string is validated
  like any other scanned value.

- **Breaking:** the minimum Go version is now 1.26.0, raised from 1.25.0, in
  `go.mod` and `tools/go.mod`; CI builds, tests and gosec run on 1.26. This
  lets `internal/collections` declare the abstract interfaces with the
  self-referential constraint the collections proposal specifies, as in
  `Collection[E any, C Collection[E, C]]`, which the Go 1.25 type checker
  rejected with "invalid recursive type".
- **Breaking:** `types.Set.Difference` now returns the asymmetric difference
  (the elements of the receiver that are not in the argument), as specified by
  the collections proposal. It previously returned the *symmetric* difference,
  which is now `types.Set.SymmetricDifference`. Like the array literal and
  parser changes above, this does not produce a compile error — review any
  call site that relies on the old meaning.
- **Breaking:** `types.Set.ContainsAll` takes an `iter.Seq[T]` instead of
  variadic values. Use `set.ContainsAll(slices.Values(vals))`.
- `types.Set.UnmarshalJSON` had a dead branch: it assigned nil for JSON
  `null` without returning, then fell through to `json.Unmarshal` and
  re-allocated in the following nil check, so the assignment could never be
  observed and `null` produced an allocated empty set. It now returns
  directly, so `null` yields the nil set as its documentation implies.
- **Fixed:** a set-map collapsed the nil and the empty set into the same
  wire value. `uu.IDSet.Value` wrote SQL `NULL` for an allocated empty set
  instead of the empty array `{}`, so storing an empty set silently nulled
  the column; `uu.IDSet.MarshalJSON` wrote JSON `null` for it instead of `[]`;
  and `types.Set.MarshalJSON` did the same. All three delegated to
  `AsSortedSlice`/`Sorted`, which return a nil slice for an empty set.
  `email.AddressSet.Value` already got this right.

  The nil, empty and populated set are now three distinct wire values, in
  both directions:

  | Go value      | SQL         | JSON        | Types                          |
  |---------------|-------------|-------------|--------------------------------|
  | nil map       | `NULL`      | `null`      | SQL: `uu.IDSet`,               |
  | empty map     | `{}`        | `[]`        | `email.AddressSet`.            |
  | populated map | `{"a","b"}` | `["a","b"]` | JSON: `uu.IDSet`, `types.Set`. |

  Only the types listed have the codec in question. `email.AddressSet` and
  `strutil.StringSet` declare no `MarshalJSON`, so `encoding/json` uses Go's
  default map encoding for them (`{"a@example.com":{}}`) — unchanged by this
  release, but do not assume the JSON column of the table above applies to
  them. `types.Set` and `strutil.StringSet` have no SQL codec at all.

  `null`/`NULL` yields a nil map, which panics when inserted into exactly
  like any nil Go map: nil-check before `Insert`, or use the pointer-receiver
  `Add` where one exists.
- `email.AddressSet.String` returns `"<nil>"` for a nil set instead of the
  empty string, matching `types.Set.String`. An allocated empty set still
  renders as the empty string, so the two are now distinguishable in a log
  line. `email.AddressSet.AddressList` is unchanged and still returns the
  joined list, which is empty for both.
- **Breaking:** `Delete` now reports whether the set changed on all four set
  types, so its signature goes from `Delete(E)` to `Delete(E) bool`. Existing
  statement calls keep compiling unchanged, but three things do not:
  an interface declaring `Delete(E)` is no longer satisfied by these types,
  a method value typed `func(E)` no longer type checks, and neither does a
  method expression such as `uu.IDSet.Delete` typed `func(uu.IDSet, uu.ID)`.
  All three are compile errors, not silent behaviour changes.
- Nil sets are documented as valid empty sets for every read and for removals.
  `Insert`, `InsertAll`, `UnionWith` and `SymmetricDifferenceWith` panic on a
  nil set, exactly like an assignment to a nil Go map.
- `email.AddressSet` keeps its pointer-receiver `Add`, `AddSet`,
  `AddNormalized` and `AddAddressPart` methods, which allocate the underlying
  map and therefore work on a nil variable or struct field. They are the
  nil-safe counterparts of the value-receiver `Insert` and `UnionWith` that the
  abstract interface requires.

### Deprecated

Still present and working, scheduled for removal before `v1.0.0`:

| Deprecated              | Replacement                               |
|-------------------------|-------------------------------------------|
| `Add(v)`¹               | `Insert(v) bool`                          |
| `AddSlice(s)`           | `InsertAll(slices.Values(s))`             |
| `AddSet(other)`¹        | `UnionWith(other)`                        |
| `DeleteSlice(s)`        | `DeleteAll(slices.Values(s))`             |
| `DeleteSet(other)`      | `DifferenceWith(other)`                   |
| `IDSet.AddIDs(ids)`     | `InsertAll(slices.Values(ids.AsSlice()))` |
| `IDSet.AsSortedSlice()` | `Sorted()`                                |

¹ Neither is deprecated on `email.AddressSet`. Its pointer-receiver `Add` and
`AddSet` allocate the underlying map, so they have different nil semantics than
the value-receiver `Insert` and `UnionWith` and are kept as their nil-safe
counterparts, see above.

The `set` package is superseded by `mapset` for new code but is unchanged and
not deprecated.

### Removed

- **Breaking:** `uu.IDSet.Diff` and `strutil.StringSet.Diff`, which returned the
  symmetric difference. Use `SymmetricDifference` — or `Difference` if the
  asymmetric difference was what was meant.

### Performance

- `strutil.TrimSpace` and `strutil.TrimSpaceBytes` gained an ASCII fast path
  that avoids decoding runes and calling through a function value, falling
  back to the rune based predicate at the first non-ASCII byte.
